# Career Quest — контекст проекта

Обновлено: 2026-09-23

Источники истины:

1. Официальное ТЗ Halyk — требования кейса.
2. Неизменённый локальный dataset версии 1.0 — факты о данных.
3. Решения пользователя, перечисленные ниже, — продуктовая и техническая политика.
4. Код и тесты репозитория — единственный источник статуса реализации.

Исходный dataset, официальное ТЗ в DOCX, ZIP и исследовательский отчёт в
репозитории не хранятся.

## A. Требования Halyk

Career Quest — веб-приложение с AI-слоем для развития сотрудников. Обязательный
сценарий: профиль сотрудника → карьерная траектория → 1–3 релевантных шага с
объяснением → выполнение активности → обновление прогресса.

Обязательная часть:

- профиль с ролью, грейдом, навыками, историей и следующими шагами;
- требования следующего уровня и понятный расчёт прогресса;
- AI-рекомендация 1–3 активностей;
- объяснение минимум по трём факторам; в ТЗ перечислены грейд, разрывы навыков,
  история участия и требования следующего уровня;
- простой HR-экран: частые разрывы, сотрудники без следующего шага, участие по
  активностям;
- загрузка дополнительных профилей и истории в формате dataset;
- разграничение прав Employee и HR, приватность данных вовлечённости;
- отклик интерфейса до 2 секунд, AI-рекомендация до 10 секунд;
- воспроизводимый запуск проекта одной командой.

Критерии оценки из официального ТЗ:

- соответствие задаче и работоспособность — 25;
- техническая реализация — 25;
- README и воспроизводимость — 25;
- ценность и применимость — 15;
- потенциал развития и оригинальность — 10.

ТЗ запрещает однофакторное правило под видом AI, публичный рейтинг сотрудников,
механику вокруг обязательных процессов и реальные персональные данные.
Геймификация — надстройка, а не обязательное ядро.

Дополнительные награды, внутренняя валюта, recognition, менторские механики,
прогноз оттока, расширенный HR-дашборд, интеграции с мессенджерами и календарями
не входят в текущий этап.

## B. Факты исходного dataset

Dataset синтетический, версия `1.0`. Бизнес-дата находится в
`meta.as_of_date`; в выданном наборе это `2026-10-01`.

Проверенные объёмы:

- 60 навыков;
- 32 role profiles: 8 ролей × 4 грейда;
- 200 сотрудников;
- 40 событий;
- 2 743 записи истории за `2024-10-01`–`2026-09-30`.

Файлы: `skills.json`, `employees.json`, `events.json`,
`activity_history.csv`. Записи JSON/CSV англоязычные. Русский и казахский текст
есть в README dataset, но переводы сущностей в самих данных отсутствуют и не
считаются готовыми.

Существенные правила и наблюдения:

- отсутствующий ключ в `employees.skills` означает уровень 0;
- `employees.skills` — оценка на `last_review_date`, а не обязательно состояние
  на дату среза;
- обязательные активности не являются целью рекомендации;
- `EV_036` — разрешённая повторяемая добровольная активность;
- в исходной истории после `completed` также повторяются `EV_001`–`EV_003`;
  исходные строки не исправляются и не удаляются;
- историческая добровольная активность могла соответствовать предыдущему
  грейду, поэтому история не бракуется по текущей аудитории события;
- фраза ТЗ «минимум три фактора» перечисляет четыре фактора. Продукт учитывает
  все четыре, а при отсутствии истории честно показывает её отсутствие;
- исходные расчётные метрики из research не считаются доказанными без
  повторного расчёта кодом.

Сверка M1 подтвердила основные объёмы Cursor и research. Агрегированные
результаты нового расчёта зафиксированы в `docs/CHECKPOINT.md`.

## C. Утверждённые пользователем решения

### Продукт и пользователи

Карьерный навигатор сотрудника:

`профиль → требования следующего уровня → подходящие активности → AI-объяснение
→ выполнение → обновление навыков и рекомендаций`.

Employee видит собственное развитие. HR видит частые разрывы навыков,
сотрудников без следующего шага и участие по активностям. Публичного рейтинга
сотрудников нет.

### Стек и эксплуатация

- backend: FastAPI и Python 3.10+;
- frontend: React 19 / Vite 8;
- постоянное хранилище: PostgreSQL, SQLAlchemy, Alembic;
- AI: OpenAI Responses API, модель из `OPENAI_MODEL`;
- production-план: Nginx + systemd, без Docker. Deploy ещё не выполнен.

Dataset передаётся загрузчику путём из `DATASET_PATH`. Абсолютного пути в коде
нет. Raw dataset в git не хранится.

### Интерфейс

Одно адаптивное веб-приложение: широкая раскладка на ПК и компактные карточки
на телефоне. Основной язык MVP — русский. Это не два приложения. PWA и отдельные
Android/iOS-приложения сейчас не разрабатываются.

### Вход и права

Сервер хранит сессию в HttpOnly cookie и проверяет CSRF. Роль берётся из
учётной записи, не из тела запроса. Employee не читает чужой профиль. HR-маршруты
закрыты сервером.

Обычный вход — `POST /api/auth/login` с username и password.

Для hackathon demo утверждён `POST /api/auth/demo-login` с телом
`{"role":"employee"}` или `{"role":"hr"}`. Сервер сам выбирает настроенный
аккаунт. Это demo entry хакатона, не production authentication. Регистрации,
SMS/OTP и отдельной админки нет.

### Карьерная траектория

Основная цель всегда является следующим грейдом текущей роли:

`Junior → Middle → Senior → Lead`.

`career_goal` сохраняется и показывается отдельно. Межролевой `career_goal` не
подменяет основную цель. Для Lead возвращается честное состояние «следующий
грейд в каталоге отсутствует». Выполнение требований не означает автоматическое
повышение сотрудника.

### Детерминированное расчётное ядро

Актуальные навыки каждый раз пересчитываются заново от оценки на
`last_review_date`. Учитываются только `completed` записи в окне:

`last_review_date < date <= meta.as_of_date`.

Порядок стабилен: дата, затем исходный порядок CSV. Для каждого изменения
сохраняется trace. Формула:

`delta = max(0, min(gain, max_level - current))`

`new_level = current + delta`

Согласованная поправка к research: активность никогда не понижает уже имеющийся
навык. Например, уровень 5 при `max_level=4` остаётся 5. Это правило нашего
движка, а не дословная формула организатора.

Кандидат допускается, только если:

- событие не mandatory;
- текущая роль и грейд входят в аудиторию;
- prerequisites выполнены по актуальным навыкам;
- это событие сейчас не `in_progress`;
- оно не было `completed`, кроме повторяемого `EV_036`;
- есть сессия на/после бизнес-даты либо формат `self_paced`;
- есть положительный эффект хотя бы на один разрыв основной цели.

`no_show`, `declined` и `dropped` не являются пожизненным запретом. Движок
возвращает отдельные фактические счётчики по событию и связанным навыкам, не
приписывая сотруднику мотивацию.

Движок по-прежнему отдаёт candidate facts, а не выбор модели. Числового
AI-score нет. Для каждого кандидата доступны цель, затрагиваемые и critical
gaps, prerequisites, потенциальные изменения и факты участия. Отдельно
различаются:

- следующий грейд отсутствует;
- требования цели уже выполнены;
- подходящих доступных активностей нет.

### AI

Детерминированный код считает навыки, ограничения и полезный эффект. OpenAI
сравнивает только допустимые варианты и объясняет выбор по переданным фактам.
Model ID берётся из `OPENAI_MODEL`; проверка интеграции использовала
`gpt-5.6-terra`. Ответ валидируется сервером; fallback без AI явно маркируется.
Модель не создаёт мероприятия, уровни, требования или историю.
Embeddings, vector DB, NVIDIA и собственное обучение не нужны.

Отличие продукта — проверяемый ответ на вопрос: «Почему это занятие, а не
другая очевидная альтернатива?». Отдельный экран сравнения отложен до рабочего
обязательного сценария.

### Документация

`README.md` — канонический русский README. `README.kz.md` и `README.en.md` в
текущую сдачу не входят.

Model ID задаётся `OPENAI_MODEL`. Live smoke использовал `gpt-5.6-terra`.
Порядок deterministic fallback описан в `docs/API.md` и не является AI-score.

## E. M2.1: хранение и API

Доменные dataclass-модели не заменены ORM-моделями. Новый слой хранит в
PostgreSQL профили, историю, новые завершения, хеши паролей и серверные сессии.
Справочники skills, events и role profiles читаются из переданного dataset.
Исходная оценка и исторические строки отделены от завершений приложения:
исторический replay M1 не меняется, а новые действия применяются отдельно и
учитываются даже при `last_review_date == meta.as_of_date`.

Обычный запуск не удаляет таблицы. Повторный seed с тем же отпечатком dataset
не дублирует данные и не сбрасывает прогресс; другой dataset не перезаписывает
хранилище молча. Миграции разрешены только для баз `career_quest_dev` и
`career_quest_test`.

HTTP-контракт зафиксирован в `docs/API.md`. `GET /candidates` остаётся сырыми
фактами с `used_ai=false`. `GET /recommendations` отправляет в OpenAI Responses
API только роль, грейд, цель и допустимые факты занятий. Модель задаётся
`OPENAI_MODEL`. В live smoke ответил `gpt-5.6-terra` за 7883 мс и вернул три
ID из candidate set. Чужой ID, таймаут и ошибка провайдера дают
`fallback_ranked` по прозрачному порядку фактов, без числового AI-score.
Ключ в git не входит.

PostgreSQL 14 проверен через SSH-туннель: миграция, seed, перезапуск, повтор
запроса и два параллельных completion. Базы только `career_quest_dev` и
`career_quest_test`. База `hackathon` не изменялась.

## D. Текущие ограничения

Реализованы backend API, PostgreSQL, auth, AI recommendation, completion,
HR overview/import и React/Vite клиент. Подробный статус — `docs/CHECKPOINT.md`.

Остаётся:

- hackathon demo-login рядом с обычным login;
- `skill_id` в UI, потому что API профиля не отдаёт display name навыка;
- отдельные экраны «Карьерный путь» и «История» не сделаны и не являются
  обязательным сценарием;
- на integration commit UI не показывает server-ranked fallback;
- полный запуск сайта одной командой отсутствует;
- deploy, Nginx, systemd, DNS и live demo не выполнены.

PWA, нативные приложения и награды не входят в обязательный объём.

## Реализованная архитектура

```text
dataset path
    ↓
validated loader
    ↓
deterministic Career Engine
    ↓
PostgreSQL

React/Vite
    ↓
FastAPI
    ├ auth / sessions / CSRF
    ├ employee profile, recommendations, completion
    ├ HR overview / import
    └ AI recommendation layer
         получает только допустимых candidates
         validates IDs, factors, ranks
         fallback без вызова модели как будто она ответила
```

Расчётный модуль не зависит от FastAPI, PostgreSQL и OpenAI.
`GET /api/health` проверяет только процесс. Готовность БД — `GET /api/ready`.
